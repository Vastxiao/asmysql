### New Features

#### 1. Connection Init SQL (`init_sql`)

Added `init_sql` parameter to automatically execute preset SQL on each new TCP connection's first use. Ideal for ClickHouse async insert configuration, MySQL session variable setup, and similar scenarios.

**Background**:

In databases like ClickHouse, `SET` statements are scoped at the TCP connection level. Previously, `SET` had to be manually executed before every `INSERT` to configure async insert parameters, which was redundant and inefficient. The `init_sql` feature moves this capability down to the engine layer for automatic per-connection initialization.

**How It Works**:

- After `connect()` creates the pool, `pool.acquire()` is automatically wrapped
- Uses `weakref.WeakSet` to track initialized Connection objects
- Executes `init_sql` on first acquire of a new connection; skips on subsequent reuses
- When a connection is recycled via `pool_recycle`, the new connection re-executes `init_sql`
- If `init_sql` execution fails, the exception propagates upward for proper error handling

**Usage**:

```python
from asmysql import Engine

# Via keyword argument
engine = Engine(
    host="192.168.62.195",
    port=9004,
    user="default",
    password="",
    init_sql=(
        "SET async_insert = 1, wait_for_async_insert = 0, "
        "async_insert_busy_timeout_ms = 1000, "
        "max_execution_time = 30"
    ),
)
await engine.connect()

# Via URL parameter
engine = Engine(
    url="mysql://user:pass@127.0.0.1:3306/?init_sql=SET SESSION wait_timeout=600"
)
await engine.connect()
```

**Backward Compatible**:

`init_sql` defaults to `None`. When not provided, behavior is identical to v2.0.0 — no impact on existing code.

### Bug Fixes

- **Fix connection leak in `Result.__call__()` error path**: When SQL execution raised `MySQLError`, `cursor.connection` became `None` after `cursor.close()`, causing `pool.release(None)` to trigger `AssertionError` and permanently leak the connection. Fixed by holding the connection reference in a local variable and checking for `None` before release
- **Fix inverted `close` parameter condition in `fetch_many()`**: The condition `if close is None:` was accidentally inverted, causing `__conn_autoclose` to be set to `None` (falsy) on default calls, preventing automatic connection release after data consumption
- **Fix `close()` not idempotent and unguarded**: Duplicate calls triggered double `pool.release()` causing `AssertionError`; when `cursor.close()` raised an exception, `release` was skipped causing a connection leak. Fixed by extracting the cursor and nullifying it first, with `try/finally` to guarantee release
- **Fix double close in `__anext__()`**: `fetch_one()` already called `close()` when returning `None`, and the redundant `close()` call in `__anext__()` caused double `pool.release()`
